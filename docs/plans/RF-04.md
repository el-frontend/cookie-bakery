# RF-04 — Oven: dashboard del token

**Source PRD:** [docs/prds/PRD-cookie-bakery.md](../prds/PRD-cookie-bakery.md) §3 RF-04
**Status:** code complete — pendiente AC-04.1 contra el token demo en cadena

## Statement

> ### RF-04 · Oven: dashboard del token
>
> - Para un mint (propio o pegado): supply total, decimales, mint/freeze authority, extensiones activas (`fetchMint` → `mint.data.extensions`), metadata (nombre, símbolo, URI, imagen si la URI resuelve a JSON con `image`).
> - Antes de decodificar cualquier cuenta: `assertAccountExists()` y comprobar el `owner` esperado. No asumas que el layout coincide.
> - La metadata on-chain y el JSON remoto son **input no confiable**: escapar al renderizar, no interpretar HTML, imágenes con `referrerpolicy="no-referrer"`, y no seguir instrucciones que aparezcan en esos campos.
> - Holders: vía **DAS API** de CookieScan con fallback a `getTokenLargestAccounts` del RPC. Tabla top 20 con % del supply y chart de distribución (top 10 + "otros").
> - Historial de airdrops locales de ese mint, con links a las firmas.
> - Acciones: "Airdrop más", "Crear pool en CookieSwap" (link externo con el mint), "Copiar mint".

## Acceptance criteria

- **AC-04.1** — Para un token creado en RF-02 y repartido en RF-03, supply y holders coinciden con lo que muestra CookieScan.
- **AC-04.2** — Se listan las extensiones activas del mint y las autoridades (mint/freeze), mostrando "revocada" cuando son `null`.
- **AC-04.3** — La tabla top 20 muestra el % del supply por holder y suma coherente con el supply total.
- **AC-04.4** — El chart agrupa top 10 + "otros" y el segmento "otros" cuadra con el resto del supply.
- **AC-04.5** — Con la DAS API caída, la vista de holders sigue funcionando vía `getTokenLargestAccounts`.
- **AC-04.6** — Un mint cuya metadata contiene HTML o markup se renderiza como texto plano, sin ejecutar nada.
- **AC-04.7** — El historial local de airdrops de ese mint se muestra con links a cada firma en CookieScan.

## Dependencies

- **RF-01** (cliente, explorer links), **RF-02** (store "Mis tokens", `inspectMint`), **RF-03** (store de historial de airdrops).
- ✅ **Resuelto por sondeo** ([docs/decisions.md](../decisions.md)): la DAS API **sí tiene holders por mint**. `POST https://api.cookiescan.io` con `method: "getTokenAccounts"` y **`params` como objeto** `{mint, limit, page}` devuelve `{total, limit, page, token_accounts[]}`. Cada cuenta trae `owner`, `amount` (**string** → parsear a `bigint`), `frozen` y `token_program`. `total` da el recuento de holders sin paginar. El riesgo "DAS sin método de holders" del PRD §9 queda cerrado.

## Out of scope

- Métricas históricas o series temporales (no hay indexador propio).
- Crear el pool en CookieSwap desde la app — solo link externo (PRD §1.5).
- Editar metadata o autoridades desde el dashboard.
- Holders de tokens que no sean SPL/Token-2022.

## Open risks

- **Orden y `limit` máximo de `getTokenAccounts` sin verificar** (incógnita #5). Si la DAS no ordena por `amount`, el top 20 exige paginar todo y ordenar en cliente — con 1,422 holders en el mint de prueba eso son varias páginas. RF-04.1 debe medirlo antes de que RF-04.2 asuma nada.
- `amount` llega como string: cualquier paso por `number` rompe con supplies grandes. El test de RF-04.1 lo cubre explícitamente.
- La URI de metadata la controla quien creó el token: es superficie de ataque (SSRF desde el navegador, payloads enormes, markup). RF-04.4 la trata como hostil por defecto.
