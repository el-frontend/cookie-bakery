# RF-02 — Bake: crear un token Token-2022 con metadata

**Source PRD:** [docs/prds/PRD-cookie-bakery.md](../prds/PRD-cookie-bakery.md) §3 RF-02
**Status:** code complete — pendiente un mint real en cadena (AC-02.1/.2/.3 e incógnita #4)

## Statement

> ### RF-02 · Bake: crear un token Token-2022 con metadata
>
> - Formulario: nombre (≤32), símbolo (≤10), decimales (0–9, default 6), supply inicial (número, default 1,000,000), URI de metadata (URL https opcional), descripción corta (opcional, se guarda localmente).
> - Opciones avanzadas (colapsadas): **Transfer fee** (basis points + máximo), **Mint close authority**, revocar mint authority tras el mint inicial (checkbox), revocar freeze authority (checkbox, default activado).
> - Al enviar se construye **una sola transacción** (si cabe en el límite de tamaño; si no, el planner la parte) con: `createAccount` para el mint (System) dimensionado con **`getMintSize([...extensiones])`** + `initializeMetadataPointer` + `initializeMint` + `initializeTokenMetadata` (+ `updateField`) + creación de la ATA del creador + `mintTo` del supply inicial (+ `setAuthority` para revocaciones).
> - **Orden obligatorio:** las instrucciones de extensión van **antes** de `initializeMint`.
> - Las ATAs se derivan con `findAssociatedTokenPda({ owner, mint, tokenProgram })` pasando **`TOKEN_2022_PROGRAM_ADDRESS`**.
> - Antes de firmar: simular la transacción y mostrar resumen con coste estimado (rent del mint vía `client.getMinimumBalance(size)` + rent de la ATA + fee) y saldo COOK disponible; bloquear si el saldo es insuficiente.
> - Tras confirmar: tarjeta con mint address, link a CookieScan, botón "Ir a Airdrop" y "Ver en Oven". El token se guarda en `localStorage` (lista "Mis tokens").
> - Debe existir también la opción "Token clásico (SPL Token)" sin metadata, como fallback.

## Acceptance criteria

- **AC-02.1** — El mint creado aparece en CookieScan con nombre y símbolo legibles.
- **AC-02.2** — La ATA del creador contiene exactamente el supply inicial indicado, con los decimales indicados.
- **AC-02.3** — Nightly muestra el token en la cuenta del creador.
- **AC-02.4** — El formulario rechaza nombre >32, símbolo >10, decimales fuera de 0–9 y supply ≤ 0, sin llegar a firmar.
- **AC-02.5** — Con saldo COOK insuficiente para rent + fee, el botón de envío queda bloqueado y se muestra el coste estimado frente al saldo.
- **AC-02.6** — Las revocaciones marcadas (mint/freeze authority) dejan esas autoridades a `null` en el mint on-chain.
- **AC-02.7** — El token creado queda en `localStorage` y aparece en "Mis tokens" tras recargar.
- **AC-02.8** — La opción "Token clásico (SPL Token)" crea un mint sin metadata usando el programa Token.

## Reuse (do not reinvent)

- `getMintSize()` de `@solana-program/token-2022` — nunca hardcodear 82 bytes ni sumar tamaños a mano.
- `findAssociatedTokenPda()` — no derivar PDAs manualmente.
- `client.getMinimumBalance(size)` — no usar constantes de rent.
- `client.planTransactions` / `sendTransaction` — el planner parte la tx si no cabe; no implementar troceado propio aquí.
- `src/lib/chain/explorer.ts` (RF-01.2) para los links a CookieScan.
- `src/lib/format/lamports.ts` (RF-01.6) para mostrar costes en COOK.

## Out of scope

- Subida de imágenes a IPFS/Arweave (PRD §1.5) — solo se acepta una URL ya existente.
- Edición de metadata después de crear el token.
- Reparto del supply → RF-03.
- Vista de holders y supply on-chain → RF-04.

## Open risks

- **La extensión `TokenMetadata` podría no comportarse igual pese a estar el programa desplegado** (incógnita #4 de `docs/decisions.md`). Mitigación: RF-02.4 entrega el fallback SPL clásico en el mismo plan, no después.
- Si mint + ATA + metadata + revocaciones no caben en 1,232 bytes, el planner parte en dos transacciones y el usuario firma dos veces: la UI debe soportarlo sin dar el token por fallido entre firmas.
- Un `updateField` con descripción larga puede desbordar la tx; limitar la descripción local a lo que no se escribe on-chain.
